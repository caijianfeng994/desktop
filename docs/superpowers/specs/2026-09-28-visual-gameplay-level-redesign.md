# 小小工坊：去方块化视觉、机库改装与闯关体系改造方案

状态：实施方案（2026-09-28）。**阶段 0 止血已完成**（pytest 149 全绿、试玩脚本修复并实机验证、改动落库到 `feature/mecha-action`）。阶段 1 起进入代码实施，验收清单边做边回填。

对标画面：《机甲战魔 神话之裔》机库改装界面（左槽位零件列表 / 中机体展示 / 右参数对比面板 + 总重与总耗能仪表）。本项目借鉴其**界面信息架构与改装取舍的表达方式**，原创机体、世界与美术，不构成对该游戏功能的描述。

## 1. 核心问题与目标

当前已实现的能力集中在机制层：装配、试跑、诊断、多解挑战与战斗要素都有模块级测试覆盖（前端 `node --test` 99 项全通过，pytest 149 项全通过）。但三件事卡住了"像一款游戏"：

1. **画面是方块。** 整机由 `partVisuals.mjs` 中的 44 处 `BoxGeometry` 加少量圆柱圆环拼出，房间与废墟同理。机制再扎实，观感仍停在原型阶段。
2. **装配没有博弈。** 关卡只判"能不能跑通"（`missions_open.py:54`：block_id 匹配 + region==receive + speed<=0.05），跑通即满分，玩家没有取舍压力。
3. **没有闯关结构。** 3 个桌面委托 + 3 个试验场挑战，首页只有 `00 / 03` 进度与一章 `CHAPTER 01`，没有章节推进、关卡解锁与失败重试。

目标顺序固定：**先让界面像机库，再让画面不像方块，接着让装配有取舍，最后把内容装进关卡结构。** 反过来做会得到一个内容更多但依然像 demo 的东西。

## 2. 目标画面：机库对标的三层拆解

对标界面拆成三层，成本与性质完全不同，必须分开评估。

| 对标要素 | 项目现状 | 差距 | 成本 |
| --- | --- | --- | --- |
| 槽位 tab（头/躯干/左臂/右臂/腿）+ 零件列表 | 槽位概念已有（`workshop/mechaZones.mjs` 的 `zoneForPart`） | 缺 UI 布局 | 小 |
| 右侧参数面板与 Compare 对比 | `editor/hangarMetrics.mjs`、`simulation/structureContrast.mjs` 数据齐全 | 缺面板 UI | 小 |
| 总重 / 总耗能仪表 | `game/engine.py` 的 `power()` 供电预算已有 | 缺仪表 UI | 小 |
| 排序 / 筛选 / 收藏 / 目录计数 | 零件目录已有（`game/parts.py`） | 缺 UI | 小 |
| 高精度机甲模型（分层装甲、硬表面、PBR） | 程序化几何拼装 | **最大差距** | 大，且是美术工作 |
| 暗色机库、bloom、地面反射、ACES 色调映射 | 明亮房间风，vendor 无后处理 | 缺 postprocessing 与灯光重做 | 中 |
| 待机展示动画与切换运镜 | 仅 orbit 相机 | 无动画 | 中 |

**三层结论：**

- **信息层（已有 90%，纯前端工作）**：把 `build` 视图重排成"左列表 / 中渲染 / 右参数"的机库布局，数值全部来自现成模块。收益立竿见影。
- **渲染层（中等成本，代码工作）**：vendor 需补 r160 配套的 `postprocessing`（EffectComposer、UnrealBloomPass、OutputPass）与 `loaders/GLTFLoader.js`——目前 vendor 下只有 `three.module.js` 和 `controls/OrbitControls.js`。暗机库、轮廓光、地面反射接入现有画质分档（高/中/低）开关。
- **资产层（决定成败，且不是代码工作）**：对标机甲是数万三角面的硬表面模型。程序化几何**到不了这个水平**。需要分槽位 GLB（HEAD/BODY/ARM/LEGS 各自独立 + 统一挂点）、减面到实时可用、法线与粗糙度贴图。来源三条：Blender 手作、CC0 模型库（Kenney / Quaternius / Poly Pizza）、AI 生成后减面（`studio/image_to_3d.py` 产出面数不可控，只够头像级，做不了机甲零件）。

**诚实预期**：做完信息层与渲染层，得到"界面与数值 95% 像对标、模型 30% 像对标"的机库；资产层不做，画面永远差最后一口气。

## 3. 视觉：从方块到机械

### 3.1 改造入口是收敛的

唯一入口是 `src/desktop_robot/studio/static/game/workshop/partVisuals.mjs:61` 的 `createPartVisual(partId, size, opts)`。编辑器、试验场、结构对比都经过它取视觉，改这一个函数即可换掉整机外观，不需要动装配逻辑、碰撞或保存格式。

配套约束点必须同步：

- `placePartVisual`（同文件 397 行）：摆放与朝向。
- `expectedMeshCount`（同文件 412 行）：网格数量断言。
- `tests/test_game_part_visual_scale.mjs`：视觉尺寸与物理尺寸的对应。**这是硬约束**——视觉一旦与碰撞盒、挂点脱节，已有的可达半径、轮距、倾覆裕度全部失真，物理玩法就废了。

### 3.2 三档路线

| 档 | 做法 | 依赖 | 风险 |
| --- | --- | --- | --- |
| A 程序化升级 | Box → 倒角挤出（`ExtrudeGeometry` + `bevelEnabled`）；轮毂/电机壳 → `LatheGeometry`；臂杆 → `CapsuleGeometry`；保留已有 `TorusGeometry` 轮缘；材质沿用 `stdMat` / `accentMat` / `darkMetal`，补 canvas 程序化生成的法线与粗糙度贴图 | 无外部依赖 | 低，上限受限 |
| B 场景去方块 | `yardScene.mjs` 的 9 处 Box 改为地形高度场（`simulation/terrain.mjs` 已有）+ `InstancedMesh` 批量道具 | 无 | 中，需重测碰撞 |
| C 英雄零件 GLB | 仅机体、夹爪、轮子、机甲外壳等"英雄零件"用 GLB，结构件保留程序化 | 需 GLTFLoader + 资产 | 中高 |

### 3.3 引入 GLB 前必须知道的三件事

1. **vendor 里没有 GLTFLoader**，需补 r160 配套的 `loaders/GLTFLoader.js` 及其依赖。
2. **静态路由已经存在**：`http_server.py:114` 的 `/game-assets/` 映射到 `static/game/`，`.glb` 放进去即可取用，无需改后端。
3. **生成链路可用但不可控**：`studio/image_to_3d.py`、`make_it_animatable.py`、`glb_inspect.py` 已存在，但依赖外部 Space，产出面数与拓扑不适合直接进实时场景，必须经 `glb_inspect` 检查并减面。

### 3.4 回落策略（不可省略）

建立零件模型表（如 `PART_MODEL_MAP = {partId: url}`），在 `createPartVisual` 中查表：

- 有 GLB 且加载成功 → 用 GLB；
- 加载失败 / 超时 / 文件缺失 → **回落程序化几何，并在调试 HUD 记一条警告**；
- 画质分档为低时（现有 `yard-quality-low`）→ 强制程序化。

没有回落，一次加载失败就是空场景，玩家看不到自己的机器。

## 4. 机库信息层（阶段 1，先做）

把 `build` 视图从"参数堆叠"重排为三栏机库：

- **左栏**：槽位 tab（头 / 躯干 / 左臂 / 右臂 / 腿，复用 `mechaZones.mjs`）+ 该槽位零件列表（缩略图 + 名称 + 编号）+ 目录计数。
- **中栏**：机体实时展示，沿用已有 orbit 相机与标准视角（`cameraRig.mjs`），底部留画质分档与调试 HUD。
- **右栏**：参数面板（质量 / 可达 / 轮距 / 倾覆裕度 / 功耗 / 接口），取自 `hangarMetrics.mjs`；对比切换取自 `structureContrast.mjs`，呈现"当前方案 vs 对照方案"的红绿差异；标签 chips 表达设计特征（轻量底盘 / 可爬坡 / 双臂装卸）。
- **顶栏**：总耗能 `power()` 与总重仪表。

缩略图优先用离屏渲染生成，无缩略图时回落到色块占位，不得因缺图阻塞界面。

## 5. 装配游戏化：给玩家取舍

### 5.1 关卡装配契约

复用现成的供电预算与接口占用（`game.html` 中的 `power-label` / `port-dots`），升级为每关硬约束：功耗上限、接口数量、外形尺寸上限、必须具备的能力（抓取 / 越障 / 举高 / 战斗）、关卡特有约束（窄门 0.25m 限宽、坡面扭矩）。

### 5.2 结算多指标化

现在的成功判定只有三条件，改成多档结算：完成度、用时、能耗、结构冗余（倾覆裕度、可达余量）。

### 5.3 保住多解，别给最优解

`apply-starter-loadout` 当前是一键最优解，会抹掉已有的多解设计。改成：**给出约束，留两三个可行解**。抽屉取物的 grasp / push / drag 三路径、机甲的 ground fire / winch / thrust 三流派已有模块级验证，这是本作最值钱的资产。

## 6. 闯关体系

### 6.1 数据结构

扩展 `missions_open.py:43` 的 `OPEN_CHALLENGES`，每关增加 `chapter` / `order` / `prereq` / `constraints` / `par`，沿用已有的 `reward` / `xp` / `loot` / `block_id`。

### 6.2 UI 与进度

`game.html:28` 已有 `CHAPTER 01` 与 `chapter-dots`，扩成章节地图（章节节点 + 关卡节点 + 解锁/已完成/可挑战三态）。进度沿用 `engine.py:102` 的 `completed_challenges`，增加解锁态与失败重试计数；奖励防重复逻辑（`first` 判定）已实现，直接沿用。`start_challenge` / `submit_challenge`（`engine.py:464` / `481`）增加失败态与重试入口。

### 6.3 内容组织

复用现有三关玩法内核（夹/推/拖、抬高/够远/绕行、战斗/绕行），按 3 章 × 3 关组织，每章引入一个新机制（绞盘、推进、重甲）。章节推进的意义是**让玩家带着上一章改出来的机器进入下一章**，而不是每关重新配装。

- [x] 机库三栏在常见桌面尺寸与窄窗口下均可操作，不遮挡关键控件。（2026-09-28 浏览器实测：槽位 tab、调色板、中栏画布、右栏参数均可操作；窄窗口待补充）
- [x] 切换槽位后零件列表与当前机体一致，换件后参数面板实时更新。（实测：切「肩」tab 显示装甲件；装四轮模板后质量/可达/倾覆/供电实时联动）

- [x] 整机与场景中不再有作为主体的裸露方块堆。（阶段 2 程序化：全部 `BoxGeometry` 换成倒角 `rbox`，零控制台错误，build/yard 浏览器实测渲染正常；但倒角只软化棱角，轮廓仍由箱体派生，真正的造型跨越在阶段 6 英雄零件 GLB）
- [x] `tests/test_game_part_visual_scale.mjs` 通过；视觉尺寸与碰撞盒、挂点一致。（阶段 2 改几何后重跑：node 99 + pytest 149 全绿；`rbox` 实测倒角后包围盒精确等于 (w,h,d)，不破坏可达/轮距/倾覆计算）
- [ ] 模型加载失败、超时或文件缺失时回落程序化，调试 HUD 有警告。（阶段 6）
- [ ] 低画质分档强制程序化并关闭后处理，帧率不因特效下降。（阶段 3）
- [ ] 每关有明确装配约束，且至少两种机制不同的解法可通过。
- [ ] 结算区分完成、用时、能耗与结构冗余，跑通不等于满分。
- [ ] 章节地图显示解锁、已完成与可挑战三态；前置未完成则不可进入。
- [ ] 失败可重试，重试不丢失作品、不重复发放奖励。

### 阶段 1 实施说明（2026-09-28）

改动集中在前端，不动装配逻辑、碰撞与保存格式：

- `game.html`：build 视图左栏改为「槽位 tab + 动态调色板 + 目录计数」，banner 加顶栏三指标，右栏加「对照·工程机甲参考」对比块。
- `game.js`：新增 `renderBuildPalette()`（按 `PART_ZONE` 把 `FREEFORM_PARTS` 分组到 头/躯干/肩/底盘/臂/背包/武器/配件）、`renderHangarCompare()`（当前蓝图 vs 工程机甲参考，质量/可达/轮距/倾覆裕度差值）、`renderHangarTopStats()`（总重/供电估/零件数）。
- `mechaZones.mjs`：导出 `PART_ZONE` 并补 `battery/pusher/hook/camera/display` 的分区映射。
- `game.css`：新增 `.slot-tabs` `.slot-tab` `.hangar-topstats` `.hangar-compare` `.part-symbol` 等样式。

**数据层发现（影响后续阶段）**：build 蓝图的零件 id（`wheel`/`gripper`/`plate`）与装配态目录 `state.parts` 的 id（`wheels`/`arm`/`arm_left`）是**两套命名空间**，`state.part_defs` 序列化时还剥掉了 `power_w`。因此机库内供电为按质量折算的**估算值**（标注「供电估」）。阶段 5 做装配契约（功耗约束）时，需先让后端在 `part_defs` 里补回 `power_w`，或统一两套 id 体系。

**已知近似**：顶栏「供电估」= Σ(mass_kg)×3.2，仅作机库内部相对参考，与装配态 `state.power` 解耦，不进入存档或判定。

主要风险是美术资产工作量、模型与既有动画/挂点的兼容、加载性能，以及范围扩张。通过限定英雄零件数量、统一挂点规范、强制回落策略与逐阶段验收控制风险。**不承诺未经测量的开发周期或全设备帧率。**

### 阶段 2 实施说明（2026-09-28）

程序化去方块（A 档），最低风险、零外部依赖：

- `partVisuals.mjs`：新增 `rbox(w,h,d,r)` 助手，用 `ExtrudeGeometry` + `bevelEnabled` 做倒角，但把基础形状缩小 `2*bevelSize`，使**最终包围盒仍精确等于 (w,h,d)**（已在 Node 中实测 4 组尺寸均精确吻合）。把文件内全部 `new THREE.BoxGeometry(` 替换为 `rbox(`，默认倒角半径按最短边 14% 自适应。
- 保留既有复合外形（头/躯干/肩/腿/背包/枪 本就是多件拼装）与 `withEdges` 描边；倒角让面板棱角软化，不再读作纯方块。
- `visualHalfH = sy/2` 不变，摆放公式 `placePartVisual` 不受影响，物理玩法（可达/轮距/倾覆裕度）零失真。
- 实测：build 与 yard 浏览器零控制台错误、渲染正常；`node 99 + pytest 149` 全绿。

**诚实边界**：倒角只软化棱角，整体轮廓仍由箱体派生，距《机甲战魔》式的硬表面精模还差一档。真正的造型跨越在阶段 6（英雄零件 GLB）——但 GLB 需要美术资产（非程序活），且 vendor 当前没有 `GLTFLoader`（阶段 3 一并补）。阶段 2 已满足"不再由纯方块构成"的程序化下限。
