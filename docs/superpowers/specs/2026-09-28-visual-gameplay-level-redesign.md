# 小小工坊：去方块化视觉、装配游戏化与闯关体系改造方案

状态：产品设计提案（2026-09-28）。**尚未实现**，本文只定义方向与验收口径，不计入当前已实现能力。实现前必须先完成 §8 前置止血项。

## 1. 核心问题与目标

当前已实现的能力集中在机制层：装配、试跑、诊断、多解挑战与战斗要素都有模块级测试覆盖（2026-09-28 实测：前端 `node --test` 99 项全通过）。但三件事卡住了"像一款游戏"：

1. **画面是方块。** 整机由 `partVisuals.mjs` 中的 44 处 `BoxGeometry` 加少量圆柱圆环拼出，房间与废墟同理。机制再扎实，观感仍停在原型阶段。
2. **装配没有博弈。** 装配工作台能摆出任何结构，但关卡只判"能不能跑通"（`missions_open.py:54`：block_id 匹配 + region==receive + speed<=0.05），跑通即满分，玩家没有取舍压力。
3. **没有闯关结构。** 目前是 3 个桌面委托 + 3 个试验场挑战，首页只有 `00 / 03` 进度与一章 `CHAPTER 01`，没有章节推进、关卡解锁与失败重试。

目标顺序很明确：**先让画面不像方块，再让装配有取舍，最后把内容装进关卡结构里。** 反过来做会得到一个内容更多但依然像 demo 的东西。

## 2. 视觉：从方块到机械

### 2.1 改造入口是收敛的

唯一入口是 `src/desktop_robot/studio/static/game/workshop/partVisuals.mjs:61` 的 `createPartVisual(partId, size, opts)`。编辑器、试验场、结构对比都经过它取视觉，改这一个函数即可换掉整机外观，不需要动装配逻辑、碰撞或保存格式。

配套两个约束点必须同步：

- `placePartVisual`（同文件 397 行）：摆放与朝向。
- `expectedMeshCount`（同文件 412 行）：网格数量断言，改几何后要跟着改。
- `tests/test_game_part_visual_scale.mjs`：视觉尺寸与物理尺寸的对应。**这条是硬约束**——一旦视觉与碰撞盒、挂点脱节，已有的可达半径、轮距、倾覆裕度全部失真，物理玩法就废了。

### 2.2 三档路线，按序推进

| 档 | 做法 | 依赖 | 风险 |
| --- | --- | --- | --- |
| A 程序化升级 | Box → 倒角挤出（`ExtrudeGeometry` + `bevelEnabled`）；轮毂/电机壳 → `LatheGeometry`；臂杆 → `CapsuleGeometry`；保留已有 `TorusGeometry` 轮缘；材质沿用 `stdMat` / `accentMat` / `darkMetal`，补 canvas 程序化生成的法线与粗糙度贴图 | 无外部依赖 | 低，上限受限 |
| B 场景去方块 | `yardScene.mjs` 的 9 处 Box 改为地形高度场（`simulation/terrain.mjs` 已有）+ `InstancedMesh` 批量道具，房间与废墟不再用方块堆 | 无 | 中，需重测碰撞 |
| C 英雄零件 GLB | 仅机体、夹爪、轮子、机甲外壳等"英雄零件"用 GLB，结构件保留程序化 | 需新增 GLTFLoader + 资产 | 中高 |

### 2.3 引入 GLB 前必须知道的三件事

1. **vendor 里没有 GLTFLoader。** `static/vendor/three/` 下只有 `three.module.js`（r160）与 `controls/OrbitControls.js`，需自行补入 r160 配套的 `loaders/GLTFLoader.js` 及其依赖。
2. **静态路由已经存在。** `http_server.py:114` 的 `/game-assets/` 直接映射到 `static/game/`，`.glb` 放进去即可取用，无需改后端。
3. **生成链路可用但不可控。** `studio/image_to_3d.py`（图生 3D）、`make_it_animatable.py`（绑骨）、`glb_inspect.py`（检查）已存在，但依赖外部 Space，产出面数与拓扑不适合直接进实时场景，必须经 `glb_inspect` 检查并减面后再用。

### 2.4 回落策略（不可省略）

建立零件模型表（如 `PART_MODEL_MAP = {partId: url}`），在 `createPartVisual` 中查表：

- 有 GLB 且加载成功 → 用 GLB；
- 加载失败 / 超时 / 文件缺失 → **回落程序化几何，并在调试 HUD 记一条警告**；
- 画质分档为低时（现有 `yard-quality-low`）→ 强制程序化。

没有回落，一次加载失败就是空场景，玩家看不到自己的机器。

## 3. 装配游戏化：给玩家取舍

### 3.1 关卡装配契约

复用现成的供电预算与接口占用（`game.html` 中的 `power-label` / `port-dots`，逻辑在 `game/engine.py` 的 `power()`），升级为每关的硬约束：

- 功耗上限、接口数量、外形尺寸上限；
- 必须具备的能力（抓取 / 越障 / 举高 / 战斗）；
- 关卡特有约束（例如窄门 0.25m 限宽、坡面需要扭矩）。

### 3.2 结算多指标化

现在的成功判定只有三条件，改成多档结算：完成度、用时、能耗、结构冗余（倾覆裕度、可达余量）。结构对比模块 `structureContrast.mjs` 已有能力，可直接用于"我的方案 vs 参考方案"复盘。

### 3.3 保住多解，别给最优解

`apply-starter-loadout`（应用推荐装配）当前是一键最优解，会直接抹掉已有的多解设计。改成：**给出约束，留两三个可行解**，让玩家自己选。抽屉取物的 grasp / push / drag 三路径、机甲的 ground fire / winch / thrust 三流派已有模块级验证，这是本作最值钱的资产，不能被一键装配磨平。

## 4. 闯关体系

### 4.1 数据结构

扩展 `missions_open.py:43` 的 `OPEN_CHALLENGES`，每关增加字段：

- `chapter` / `order`：章节与关内序号；
- `prereq`：前置关卡 id（已完成才可进入）；
- `constraints`：§3.1 的装配契约；
- `par`：目标用时，用于结算分档；
- 沿用已有的 `reward` / `xp` / `loot` / `block_id`。

### 4.2 UI 与进度

- `game.html:28` 已有 `CHAPTER 01` 与 `chapter-dots`，扩成章节地图：章节节点 + 关卡节点 + 解锁/已完成/可挑战三态。
- 进度层沿用 `engine.py:102` 已有的 `completed_challenges`，增加解锁态与失败重试计数；奖励防重复逻辑（`first` 判定）已实现，直接沿用。
- `start_challenge` / `submit_challenge`（`engine.py:464` / `481`）增加失败态与重试入口。

### 4.3 内容组织

不新造机制，复用现有三关的玩法内核（夹/推/拖、抬高/够远/绕行、战斗/绕行），按 3 章 × 3 关组织，每章引入一个新机制（绞盘、推进、重甲）。章节推进的意义在于**让玩家带着上一章改出来的机器进入下一章**，而不是每关重新配装。

## 5. 技术迁移与模块职责

| 模块 | 现状 | 改造 |

## 6. 分阶段实施与验收

阶段门槛以**完整可玩行为**为准，不以按钮、文件或零件数量计算完成度。每阶段完成后必须回填 §7 清单，不得只勾选不记录。

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 0：止血 | 红灯清零、改动落库、试玩脚本修复 | 两条回归线能真实报警 |
| 1：视觉去方块（程序化） | 倒角挤出、车削、胶囊几何与程序化贴图 | 整机不再由纯方块构成，尺寸断言仍绿 |
| 2：场景去方块 | 地形高度场与实例化道具 | 房间与废墟不再是方块堆，碰撞未退化 |
| 3：闯关体系 | 章节数据、解锁、章节地图、失败重试 | 能从第一章连续玩到第三章 |
| 4：装配契约与多档结算 | 关卡约束、多指标结算、多解保留 | 同一关至少两种可行解，跑通不等于满分 |
| 5：英雄零件 GLB | 模型表、GLTFLoader、回落策略 | 加载失败不空场景，低画质回落程序化 |
| 6：内容扩展 | 新敌人、新区域、作品展示 | 按真实玩家反馈选择方向 |

## 7. 验证清单与风险控制

- [ ] 整机与场景中不再有作为主体的裸露方块堆。
- [ ] `tests/test_game_part_visual_scale.mjs` 通过；视觉尺寸与碰撞盒、挂点一致。
- [ ] 模型加载失败、超时或文件缺失时回落程序化，调试 HUD 有警告。
- [ ] 低画质分档强制程序化，帧率不因模型加载下降。
- [ ] 每关有明确装配约束，且至少两种机制不同的解法可通过。
- [ ] 结算区分完成、用时、能耗与结构冗余，跑通不等于满分。
- [ ] 章节地图显示解锁、已完成与可挑战三态；前置未完成则不可进入。
- [ ] 失败可重试，重试不丢失作品、不重复发放奖励。
- [ ] 中断后继续，机器结构、进度与上次一致。
- [ ] 约定设备、窗口尺寸、零件数与敌人数量后测量帧耗时与加载时长，先明确测试规模再判断是否达标。
- [ ] 小规模玩家测试：记录是否主动改装再战、能否解释配置取舍、是否期待下一章。

主要风险是美术资产工作量、模型与既有动画/挂点的兼容、加载性能，以及范围扩张。通过限定英雄零件数量、统一挂点规范、强制回落策略与逐阶段验收控制风险。**不承诺未经测量的开发周期或全设备帧率。**
